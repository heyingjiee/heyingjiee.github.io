## URL到页面加载完成

```
DNS解析  （网址解析为 IP 地址，浏览器缓存、本机缓存 host、本地DNS服务器（LDNS）、根DNS服务器）
｜
TCP连接  （三次握手建立浏览器与服务器的TCP连接。https需要额外进行 TLS/SSL 握手）
｜
浏览器发起请求
｜
服务器响应页面
|
浏览器解析 HTML  -> 并行生成 Dom树、CSSOM 树 -> 等待Dom\CSSOM 树完成后，合并生成render树,绘制在屏幕上
补充：遇到 script 标签会阻塞Html解析，使用 defer 并行下载等页面解析完后执行、async 并行下载，下载完毕立即执行
|
关闭TCP连接 （四次挥手）
```

dom树和cssom树具体怎么合成成渲染树的，详细过程 ？

* 解析 HTML，生成一颗完整的 DOM Tree、CSSOM Tree

* 浏览器使用 DFS 遍历 DOM Tree，去 CSSOM 树中查找并根据优先级实时计算最终样式（Computed Style，display: none 不展示，visibility: hidden 展示），如果节点可见就创建渲染对象（Render Object）并挂载到渲染树对应父节点下

  

## https SSL握手细节

```js
首先由客户端向服务器端发送使用的协议的版本号、一个随机数和可以使用的加密方法

服务器端收到后，确认加密的方法，也向客户端发送一个随机数和自己的数字证书

客户端收到后，首先检查数字证书是否有效，如果有效，则再生成一个随机数（预主密钥），并使用证书中的公钥对随机数加密，然后发送给服务器端

服务器端接收后，使用自己的私钥对数据解密，返回 Finish 消息。


注意 ：这个时候双方都有了三个随机数，按照之前所约定的加密方法，使用这三个随机数生成一把秘钥，以后双方通信前，就使用这个秘钥对数据进行加密后再传输。
```

## 性能指标

###  性能指标

* **首次绘制时间First Paint（FP）**：从用户请求页面到浏览器**绘制第一个像素**到屏幕上的时间

- **首屏加载时间First Contentful Paint（FCP）**：从用户请求页面到浏览器**绘制第一个有意义的内容**到屏幕上的时间（有意义的内容指文本、图像、非白色背景色的`canvas/svg`元素等）
- **最大内容绘制时间Largest Contentful Paint（LCP）**：最大内容绘制时间，指页面上最大的可见元素（文本、图像、视频等）绘制完成的时间，代表用户视觉上感知到页面加载完成的时间点。
- **用户可交互时间Time to Interactive（TTI）**：可交互时间，指页面加载完成并且用户能够与页面进行交互的时间，代表用户可以开始操作页面的时间点。
- **页面总阻塞时间Total Blocking Time (TBT)**：从 FCP 到 TTI 之间阻塞的时间
- **Interaction to Next Paint （INP）**：用户访问期间发生的所有点击、点按和键盘互动的延迟时间，最终 INP 值是观测到的最长互动时间
- **累积布局偏移 CLS**：衡量网页视觉稳定性的核心指标。它量化了页面在加载和用户交互过程中，元素位置发生**意外移动**的程度 （如广告模块等异步加载后撑开页面导致的偏移，默认字体渲染待自定义字体加载后重新渲染）
- **看首字节时间 (TTFB)**：这是衡量后端响应速度的关键指标。如果TTFB过长（如>300ms），后端服务需要优化

### 推荐指标值

| 指标 | 含义                        | 良好 (绿色) |
| ---- | --------------------------- | ----------- |
| FCP  | 首次内容绘制 (白屏结束)     | < 1.8 秒    |
| TTI  | 可交互时间                  | < 3.8 秒    |
| TBT  | 总阻塞时间                  | < 200 毫秒  |
| LCP  | 最大内容绘制 (主要加载时间) | < 2.5 秒    |
| INP  | 交互到下一次绘制 (响应延迟) | < 200 毫秒  |
| CLS  | 累积布局偏移 (页面抖动)     | < 0.1       |

## ESM与Commonjs区别

| 特性         | CommonJS                                                     | ESM (ES Modules)                                             |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 适用环境     | 主要用于 Node.js 服务端                                      | 浏览器原生支持 + 现代 Node.js                                |
| 语法         | `require()` 导入，`module.exports` 导出                      | `import` 导入，`export` 导出                                 |
| 加载时机     | 运行时动态加载                                               | 编译时静态分析                                               |
| 加载方式     | 同步加载（Node.js环境）                                      | 异步加载（浏览器环境）                                       |
| 值的处理     | 导出的是值的拷贝。模块内部改动，导出不变。允许导出直接修改变量，但是不会影响模块内部变量 | 导出的是值的引用（动态绑定）。模块内部改动，导出也会同步改动。不允许导出直接修改变量 |
| Tree-Shaking | 不支持（难以静态分析）                                       | 支持（可进行枯树摇动优化）                                   |

### Vue 的虚拟 DOM缺点

**内存开销**

浏览器内存里必须同时维护两棵树：一棵是当前的真实 DOM，另一棵是内存中的虚拟 DOM 树

**计算瓶颈**

* VDOM 通常都需要遍历整棵树（或子树）来对比差异

* Vue 父组件属性改变触发 Render ，子组件如果属性也变化继续 Render（虽然会对比只有改变的才真实渲染，但是 Render 也耗费大量计算资源）。最重要的是 Render 是组件级的，而不是精确更新某个 Dom

### hash/history

Hash 模式

1. Vue Router 通过 `window.addEventListener('hashchange', ...)` 来监听 URL 中 `#` 后面内容的变化。
2. **触发导航**：当用户点击一个路由链接（如 `<router-link to="/about">`）时，Vue Router 会修改 `window.location.hash`（例如从 `#/home` 变为 `#/about`）。
3. **更新视图**：哈希值的改变触发了 `hashchange` 事件，Vue Router 在事件回调中捕获新的哈希值，并根据路由配置匹配并渲染对应的组件，整个过程都在前端完成

history 模式

1. **修改 URL**：当发生路由跳转时，Vue Router 会调用 `history.pushState()` 、`history.replaceState()`来修改 URL。（这2个API可以控制浏览器导航栏URL变更，但是不会真的发起页面请求）
2. **监听历史**：通过 `window.addEventListener('popstate', ...)` 来监听浏览器的前进/后退操作。当用户点击前进/后退按钮时，会触发 `popstate` 事件，Vue Router 在回调中处理路由逻辑。
3. **服务器配置（关键）**：与 Hash 模式不同，History 模式的 URL（如 `https://yourdomain.com/home`）是一个真实的路径。当用户**直接访问**或**刷新**这个 URL 时，浏览器会向服务器请求该路径的资源。因此，**必须在服务器上进行特殊配置**，将所有路由请求都重定向到应用的入口文件（通常是 `index.html`），否则服务器会因找不到对应资源而返回 404 错误

```js
            console.log(`获取${key}属性`)
            // Reflect为了修正 this 指向 receiver，receiver 是 Proxy(target)
            // 假设 target有个方法 getName(){ return this.name }
            // 不写 Reflect，getName会触发代理handler，this.name不会触发代理的handler
            // 写了所有的 this 也会触发
            const val = Reflect.get(target, key, receiver)
            if (val instanceof Object) {
                return new Proxy(val, handler)  // proxy 只支持一层，这样就能支持多层
            }
            return val
        }
    }

    return new Proxy(target, handler)
}
```

### keepAlive原理

作用是**缓存组件实例**，在组件切换时保留其状态，避免重复渲染和销毁重建

```js
onActivated(() => {
  // 调用时机为首次挂载
  // 以及每次从缓存中被重新插入时
})

onDeactivated(() => {
  // 在从 DOM 上移除、进入缓存
  // 以及组件卸载时调用
})
```

原理

内部维护了 keys 数组、cache 对象，两个变量缓存数据

* 如果首次加载将组件名作为 key 加到 keys 中，把 VNode 缓存到 cache 中 （VNode的componentInstance 字段就是组件实例，存储 data、computed 数据）
* 如果第二次加载，命中 keys，则直接从 cache 中取 VNode ，调用componentInstance 的 _render 方法重新渲染页面

### Diff 算法

vue2 是对比整棵组件树，对比出现不一致，就触发组件render

vue3 的 diff 算法核心在于 **静态提升**和**快速 Diff** ，只会 render 动态节点，更高效

标记特殊节点

`div` 节点会被标记 `PatchFlags.PROPS`（属性动态），文本节点会被标记 `PatchFlags.TEXT`（文本动态）。 Diff 时，算法会先检查这个标记，如果标记显示只有文本变了，Vue 3 会**直接跳过属性对比**，只更新文本。这叫“靶向更新”。



Vue 在静态编译阶段将模板分为一个个 Block 区块，区块内

* 静态节点被提升到 render 外部（静态提升，这种节点每次渲染时直接复用，不需要重新创建 VNode 对象，也不需要参与 Diff）

* 动态节点收集到数组中，动态节点分为多种，每种分别打上特殊标记。对比的时候根据不同标记采用更优的对比方式

  | PatchFlag 类型          | 含义            | Diff 时的优化行为                                            |
  | ----------------------- | --------------- | ------------------------------------------------------------ |
  | `PatchFlags.TEXT`       | 动态文本节点    | Diff 时只对比和更新文本内容，完全跳过对该节点所有属性（如 class, style, id 等）的检查 |
  | `PatchFlags.CLASS`      | 动态 Class 节点 | Diff 时只对比和更新 `class` 属性，跳过其他所有属性和文本。   |
  | `PatchFlags.PROPS`      | 动态属性节点    | Diff 时只对比和更新那些被标记为动态的属性（例如 `:id`、`:title`），跳过静态属性和文本。 |
  | `PatchFlags.FULL_PROPS` | 全动态属性节点  | 当节点的属性 key 本身是动态的时候（如 `[dynamicKey]: value`），Vue 无法预知需要对比哪些属性，只能进行全量的属性对比。 |

### ReadableStream

允许**边接收边处理**，而不需要将整个资源加载到内存中，极大地降低了内存占用，防止 OOM

其实 ReadableStream 与 Go 语言中的 Channel 很相似

* Channel 缓冲区写满阻塞生产者，为空阻塞消费者
* ReadableStream 把控制权都交个开发者

```js
// 生产者 + 缓冲区
const stream = new ReadableStream({
  // controller 是流的控制器，用来推送数据enqueue、关闭流close、抛出错误error
  
  // new ReadableStream 时同步触发，只会触发一次
  start(controller) {
    // 向缓冲区推数据
    controller.enqueue('数据')
    // 关闭，注意多次关闭会抛出错误 TypeError: Controller is already closed
    controller.close();
  },
  
  // 消费者读取数据时，且缓冲区没满就会触发（可以触发多次）
  pull(controller) {
    // 缓冲区剩余空间
    // 注意：如果第一个 chunk 就大于了缓冲区，也不会被丢弃，只不过 desiredSize = chunkSize-highWaterMark 变成负数
    if (controller.desiredSize <= 0) { // 小于 0 证明消费者速度慢
        console.log('暂停生产');
        return;
    }
    controller.enqueue('数据')
    controller.close();
  },
  // 消费者主动终止
  cancel() {
      // 这里可以添加一些清理逻辑，比如主动断开 fetchEventSource 的连接
      console.log('流被取消，正在清理资源...');
  }
}, {
  highWaterMark: 1024 , // 缓冲区上限，这里的数据没有单位，可以把他当一个数字，size函数定义了怎么计算 chunk 的尺寸
  size(chunk) {
    // 定义如何计算每个 chunk 的大小
    // 这里把字节当单位，那highWaterMark就是字节
    return chunk.length || chunk.byteLength;
  }
});


// 消费者
for await (const chunk of stream) {
  	// enqueue 每推入一次，这里就能读取一次，chunk就推入的内容
  	// 处理完毕后才会进入下一次循环
    console.log(chunk);  // 这个数据就是controller.enqueue推入的数据
  
  	// break 可以结束循环， 触发 ReadableStream 的 cancel回调
  }
```

### 热更新

**Vite 采用基于原生 ESM 的按需编译和WebSocket 实时通信机制**

流程：**文件监听 → WebSocket 通知 → 浏览器请求更新 → 局部替换**

详细：

* 页面携带 `@vite/client` 脚本，页面脚本与服务端建立 websocket 连接
* Vite采用 chokidar 监听文件变动，如果文件变动会通过 websocket 发送信息，告知页面哪个模块更新了
* 页面分析依赖图后，重新发起 http 请求更新模块、依赖更新模块的其他模块 （加上时间戳跳过缓存）
* 服务器接收到请求后，对文件进行按需编译，返回 ESM 模块代码



### 树摇

Tree shaking 的原理：它的核心原理是基于 **ES Module (ESM)** 的**静态分析**，在构建阶段（打包时）识别并移除未被引用的代码，从而减小最终打包文件的体积。 但是有的模块在加载时就有默认逻辑执行，如果仅仅靠 ES 静态分析可能会导致模块加载时的逻辑丢失，所以如果你的模块没有副作用，在 package.json 中开启 `"sideEffects": false`

## Skills

如何评估 Skills，有哪些指标？

指标：

* 效果指标

  * 正确性：Skill 是否达成了预期的目标

  * 任务成功率/通过率 ：在一批测试任务中，Skill 能够成功完成的比例

  * 泛化性：Skill 在面对未见过的任务、新的数据分布或边缘情况时，是否依然有效

* 效率与成本指标

  * 执行时间/延迟：加载 Skill 后，完成相同任务的时间是变快了还是变慢了？端到端的延迟是否在可接受范围内
  * Token 消耗：Skill 的引入是否导致Prompt 过长，从而导致消费大量的 Token
  * 执行步骤/工具调用次数：一个高效的 Skill 应该能帮助 Agent 少走弯路。例如，集成优质 Skill 后，Agent 完成复杂任务的平均步骤减少了 30%，说明其规划更加精准

* 质量与工程指标

  * 安全性：Skill 是否存在潜在风险，如未授权的文件删除、提示词注入漏洞，或是否遵守了权限边界
  * 完整性：否包含了所有关键执行步骤、先决条件和依赖说明，是否能让模型准确理解
  * 稳定性：面对同一批类似的输入，Skill 的输出质量是否保持一致，波动极小

评估方式： 

* 准备一批用例，在加载/不加载 Skills 的情况下，对比效果
* 通过用户返回，调整 Skills 内容

https服务器返回的证书内容

- **版本 (Version)**：指明证书遵循的 X.509 标准版本，目前最常用的是 V3。
- **序列号 (Serial Number)**：由证书颁发机构（CA）为每张证书分配的唯一标识符，用于识别和管理证书。
- **颁发者 (Issuer)**：签发该证书的证书颁发机构（CA）的身份信息。通常包含国家（C）、组织（O）和通用名称（CN）等字段，例如 `C=US, O=DigiCert Inc, CN=DigiCert Global G2...`。
- **使用者 (Subject)**：证书持有者的身份信息，也就是服务器的身份。对于网站证书，最关键的字段是**通用名称（CN）**，它通常是网站的域名（如 `www.example.com`）。
- **公钥有效期 (Validity)** + **公钥及其所使用的加密算法（如 RSA、ECC）**

## 项目如何管理

1、任务拆解与进度跟进

* 将需求拆解为具体的开发任务，明确任务优先级（如 P0/P1/P2）、预估工时、负责人和状态（待办、进行中、评审中、已完成）
* 使用看板持续跟踪项目进度
* 每日/每周站会同步项目进展/阻塞点。出现 delay 要及时复盘

2、代码与版本规范

* 采用如 Git Flow 工作流，确保分支管理和代码合并的有序性
* 建立强制的 Code Review 评审机制，关注代码质量

3、工程化与基建

* **脚手架与模板**：通过自定义 CLI 工具，实现项目的快速初始化和标准化配置，确保所有项目都遵循统一的目录结构、技术栈和基础配置

* **资产沉淀**：将通用 UI 组件和业务组件沉淀下来，封装通用的工具函数，避免重复造轮子
* **构建与部署优化**：
  * 利用增量构建、代码分割、Tree Shaking 等手段，缩短构建时间，优化产物体积
  * 建立自动化的测试、构建和部署流水线，实现代码提交后的自动发布

4、监控与质量保障

* **异常监控**：实时捕获 JS 错误、资源加载失败、Promise 异常等，并上报堆栈信息，快速定位问题
* **性能监控**：关注核心 Web 指标（如 LCP, FID, CLS），监控页面加载耗时、API 请求成功率等，量化用户体验
* 通过埋点了解用户真实使用路径，为产品优化提供数据支持
* 在 CI 流程中集成 ESLint、TypeScript 类型检查、测试覆盖率检查等，不达标则无法合并代码，从源头保证代码质量

5、团队与效能度量：驱动持续改进

* 鼓励团队进行技术分享，将实际开发中遇到的问题沉淀到知识库
* 建立效能看板，量化关键指标，如：构建耗时、部署频率、线上缺陷率、代码评审时长等。用数据驱动优化决策，而不是凭感觉
